## 一、幻觉分类体系定义

### 1. 幻觉判定标准

针对智能客服场景，满足以下任一条件即判定为幻觉：

1. 回复内容与官方知识库记载的事实、规则、参数存在明确冲突；
2. 系统未接入对应能力 / 接口，却谎称可查询、可操作相关业务；
3. 遗漏知识库明确标注的、影响用户决策的关键信息，导致引导建议失准；
4. 给出违反安全提示的建议，可能造成用户权益或健康损害。

### 2. 分类与严重等级

结合业务影响和错误性质，将幻觉分为 4 大类、8 子类，同时划分 3 个风险等级：

表格

| 一级分类 | 二级子类 | 说明 | 对应标注标签 | 风险等级 |
| --- | --- | --- | --- | --- |
| **事实性幻觉** | 产品参数编造 | 产品功能、规格、材质、接口等参数与知识库不符 | 参数编造 | P1（中）/ P0（核心参数） |
|  | 服务政策偏差 / 编造 | 退货、发票、发货、售后等服务规则与知识库不一致，包含完全编造和部分偏差 | 政策编造、政策偏差、优惠编造 | P0（核心权益）/ P1（一般政策） |
|  | 业务信息编造 | 退货地址、线下门店、品牌关联等业务信息无中生有 | 信息编造 | P1（中） |
| **能力性幻觉** | 查询能力越界 | 未接入数据接口，却声称查询到对应结果 | 能力越界 | P0（高） |
|  | 操作能力越界 | 无系统操作权限，却声称已完成业务操作 | 能力越界 | P0（高） |
| **风险性幻觉** | 安全误导 | 违反健康 / 安全提示，给出风险建议 | 安全误导 | P0（高） |
| **缺失性幻觉** | 关键信息遗漏 | 影响用户决策的重要提示未告知，导致建议错误 | 信息遗漏 | P2（低） |

* 风险等级说明：

- P0（高风险）：直接损害用户权益、引发重大投诉或合规风险，必须立刻修复
- P1（中风险）：造成用户预期不符，引发普通客诉，需优先优化
- P2（低风险）：影响用户决策体验，无直接权益损失，可迭代优化

## 二、自动化检测工具实现

### 1. 技术方案

采用**「知识库匹配 + LLM 一致性校验」**的两阶段检测方案，模拟真实生产环境的检测流程：

1. **召回阶段**：根据用户问题匹配对应知识库条目（本数据集已一一对应，直接输入）；
2. **校验阶段**：将「知识库原文 + 客服回复 + 幻觉分类规则」输入大语言模型，由模型完成事实一致性判断、幻觉分类和风险定级。

### 2. 检测 Prompt 设计

```
【角色】你是专业的智能客服幻觉检测工程师，需要根据给定的知识库内容，判断客服回复是否存在幻觉。

【幻觉定义】
1. 回复内容与知识库事实、规则、参数不符；
2. 系统没有对应能力/接口，却谎称可以查询或操作；
3. 遗漏影响用户决策的关键信息，导致建议错误；
4. 给出违反安全提示的风险建议。

【分类规则】
- 事实性幻觉：参数编造、政策编造/偏差、业务信息编造
- 能力性幻觉：查询能力越界、操作能力越界
- 风险性幻觉：安全误导
- 缺失性幻觉：关键信息遗漏

【输入】
用户问题：{user_question}
知识库内容：{knowledge_base}
客服回复：{system_reply}

【输出格式】仅输出以下四行，不要输出其他内容：
是否幻觉: 是/否
幻觉类型: 对应二级子类（无幻觉时填「无」）
风险等级: P0/P1/P2（无幻觉时填「无」）
判定依据: 简要判定依据
```

### 3. 核心指标

- **召回率（Recall）**：TP/(TP+FN) = 18/18 = **100%**
- **精确率（Precision）**：TP/(TP+FP) = 18/19 ≈ **94.74%**
- **F1 值**：2*Precision*Recall/(Precision+Recall) ≈ **97.30%**
- **准确率（Accuracy）**：(TP+TN)/ 总样本 = 19/20 = **95%**

### 4. 漏检与误报明细

#### 漏检 Case：无

本次检测 18 条幻觉样本全部检出，漏检数为 0（早期版本曾漏检的 h20 已成功检出）。

#### 误报 Case：h16（色差表述边界）

- 人工标注：非幻觉（回复与知识库色差提示一致）
- 检测结果：幻觉（判定依据：回复弱化色差提示，构成偏差表述）
- 误报原因：知识库提示 “图片可能与实物存在轻微色差，请以实物为准”，客服回复 “颜色基本准确”；模型将 “基本准确” 解读为对色差提示的弱化偏差，而人工标注认为整体与知识库一致，属于 “表述弱化 vs 事实不一致” 的判定边界。

### 5. 分类准确率

- 系统口径：类型与人工标注完全匹配 0/18、语义匹配 6/18——模型输出为一级大类（事实性 / 能力性 / 风险性 / 缺失性幻觉），人工标注为二级子类标签（政策编造、参数编造、能力越界等），两者口径不同，直接比对命中率低；
- 按一级大类口径复核：18 条正确检出中 16 条大类归属一致（约 88.9%）；h13（标注：安全误导 / 风险性）与 h20（标注：信息遗漏 / 缺失性）被判为 “事实性幻觉”，与各自判定依据无本质冲突，类型细分仍有优化空间。

## 四、误判原因分析

结合本次检测结果（召回率 100%、1 条误报）和客服场景特点，容易出现误判（漏检 / 误报）的场景主要有以下几类：

### 1. 缺失性幻觉的检出已改善，类型归类仍不稳定

这是幻觉检测的共性难点：

- 常规检测逻辑聚焦 “生成内容与事实的冲突”，即 “说错了什么”；
- 信息遗漏是 “该说的没说”，需要模型主动对比知识库中的**强制告知项**，判断回复是否覆盖关键决策信息；
- 本次 h20（尺码信息遗漏）已成功检出，弥补了早期版本的漏检；但模型将其归为 “业务信息编造 / 偏差” 而非 “信息遗漏” 子类，缺失类的类型区分仍有优化空间。

### 2. “表述弱化” 类回复的误报边界

h16（色差说明）是本次唯一误报：“颜色基本准确” 与知识库 “可能存在轻微色差，请以实物为准”——

- 回复未编造事实，但弱化了知识库的风险提示，是否构成 “偏差表述” 取决于判定粒度；
- 模型按严格口径判为幻觉，人工标注按核心事实一致判为非幻觉；
- 可在提示词中补充 “仅编造 / 否认关键事实才算幻觉” 的校准规则收敛该类边界。

### 3. 能力越界类依赖知识库完整性

能力越界的判定依赖知识库明确标注 “未接入接口 / 无此功能”：

- 本次 4 条能力越界样本（h03、h10、h14、h18）全部检出，得益于知识库对系统能力边界有显式说明；
- 生产环境中很多系统能力没有显式标注，容易漏检这类幻觉。

### 4. 政策偏差与政策编造的边界模糊

同样是政策错误，“完全编造” 和 “部分偏差” 没有量化标准：

- 比如发货时间从 24 小时改成 48 小时，属于偏差还是编造，不同标注者可能有不同判断；
- 分类边界的主观性会导致类型误判，但不影响 “是否幻觉” 的二分类结果。

## 五、README

### 客服幻觉检测工具

用于批量检测智能客服回复中的幻觉内容，支持多类型幻觉识别与风险定级。

#### 1. 分类体系

包含 4 大类幻觉：

- **事实性幻觉**：产品参数、服务政策、业务信息与知识库不符
- **能力性幻觉**：系统不具备的查询、操作能力，谎称可以执行
- **风险性幻觉**：违反安全提示，可能造成用户损害的错误建议
- **缺失性幻觉**：遗漏影响用户决策的关键信息

风险等级分为 P0（高）、P1（中）、P2（低）三级。

#### 2. 检测方法

采用两阶段检测方案：

1. 知识库召回：匹配用户问题对应的官方知识库条目
2. LLM 一致性校验：基于大语言模型进行细粒度事实对比，输出幻觉判定、类型和风险等级

工具支持批量输入，基于 Spring AI 对接真实 LLM API（已内置通义千问 / DeepSeek 双模型，可切换）。

#### 3. 检出率数据

在 20 条标注测试集上的效果（最新一次检测，模型 qwen-plus）：

- 准确率：95%
- 召回率：100%（18 条幻觉全部检出）
- 精确率：94.74%（1 条误报：h16 色差表述边界）
- F1 值：97.30%

剩余误差集中在 “表述弱化” 类回复的判定边界，编造型幻觉识别稳定。

#### 4. AI 工具使用说明

- 本工具基于大语言模型的事实一致性判断能力实现，无需训练，可快速适配不同业务知识库
- 基于 Spring AI 框架，支持接入通义千问、DeepSeek 等主流 LLM API
- 生产环境建议搭配知识库检索系统使用，实现端到端自动化检测
- 针对信息遗漏类漏检问题，可补充「强制告知项规则」提升召回率

| --- | --- |
| `POST /api/detect/upload` | 上传待检测样本文件（form-data，字段名 `file`），校验后保存并返回路径 |
| `GET/POST /api/detect/batch` | 同步执行批量检测，返回汇总报告 JSON，可用 `sampleFile` 参数指定样本文件 |
| `GET /api/detect/batch/stream` | SSE 流式执行，实时推送逐条样本检测进度，可用 `sampleFile` 参数指定样本文件 |
| `GET /api/detect/result/latest` | 下载最近一次批量检测生成的 Markdown 报告 |

- 点击「批量检测」先弹出上传提醒弹窗：可选择待检查数据文件（与 `task4_replies.json` 相同结构的 JSON 数组），选择后点击「上传并检测」基于该文件执行流式检测；未选择文件时点击「检测默认文件」直接检测默认样本；
- 上传的样本文件保存于 `output/uploads/`（文件名带时间戳），可通过 `GET /api/detect/batch/stream?sampleFile=<storedFile>` 重复执行检测；
- 前端「批量检测」按钮：一键触发流式批量检测，实时展示进度，完成后在对话区渲染汇总指标与逐条判定表格；
- 结果仅以 Markdown 报告输出至仓库根目录 `output/`：`detection_result_<时间戳>.md` 与 `detection_result_latest.md`，含检测概览、评估指标（混淆矩阵、精确率/召回率/F1/准确率）与逐条判定表格（含「用户提问」列），可直接阅读或交付；
- 检测配置位于 `application.yml` 的 `hallucination.detect` 节点：可切换模型（qwen/deepseek）、调整并发数/重试次数、自定义样本文件与输出目录；上传文件大小上限 10MB（`spring.servlet.multipart`）。
